# V34 AgentRun 异常与崩溃后的终态

## 必要性与分级

2026-10-07 基线 `7a8c434`。`_handle_run_agent` 的第一阶段先提交 `AgentRun(status=running)`；第二阶段成功时写入终态，普通异常仅为资源请求设置退避后重新抛出，所有权丢失则直接抛出。没有补写失败终态或历史回收。队列自身的 claim/恢复/完成保护不等于 AgentRun 历史记录恢复。

[双库进程探针](probes/agent_run_orphan_probe.py) 经 PostgreSQL 与 Turso 的真实 ORM 建表/提交，调用实际 handler；处理阶段边界分别抛出普通 RuntimeError 或执行 os._exit(73)。该边界只在第一阶段事务提交后进入。然后启动新进程调用未替换的真实 handler，消费相同一条未识别资源，再以独立进程读回历史。

四个场景均观察到：首次失败后仅一条 running/finished_at=NULL；替代运行成功后仍为 running + success，成功行 total_resources=1、unrecognized=1、dispatched=0。主探针按“失败不能永久 running”的断言实际退出 1；子进程的普通异常退出 1、实际终止退出 73、setup/inspect/recover 均退出 0。[a 结果](probes/agent-run-orphan-a-result.json) 包含逐子进程退出码、日志及原始状态。

数据取自固定 SHA 的 prod_works_v1 资源标题/GUID/torrent URL；Agent、Channel、资源 UUID、未关联状态与故障时序是明确合成。未访问 torrent URL，没有下载、真实 Redis broker 或 worker 接管；不能从本探针宣称验证了分布式租约恢复。原记录与后续成功运行的状态问题已证实，尚无数据丢失证据，保持 P2。

专用项目 rssripple-v34-agent-run-a（32891）已 down，容器/网络/卷标签为空；Turso 临时目录在全部子进程结束后清理。V29 完整 t/u 输入与运行过程未修改。

## 方案约束与取舍

1. **异常收尾和进程丢失必须一起处理**。仅补 except/finally 无法处理 os._exit/SIGKILL；仅加“运行超过 N 分钟就失败”的定时任务会误判合法慢任务。普通异常、取消、所有权丢失与实际进程消失须分别验证。
2. **建立可持久验证的执行归属**。现有 Redis context 保存 key/job_id/token，但 AgentRun 没有绑定，MemoryQueue/直接调用则没有 Redis context。设计须覆盖两种队列与直接 handler 调用，不能只接 Redis 后宣布完成。可选方向是持久执行租约、续租和条件终态更新；也可采用具备同等证明力的队列尝试绑定，但缺失状态/Redis 故障只能算 unknown，不能当作死亡证明。
3. **防止迟到写入覆盖终态**。回收和正常完成必须用相同身份及条件更新协议；失去执行权的旧进程恢复后不得把已回收的 run 改回 success，也不得覆盖替代运行的 Agent 最近状态。继续使用 B4 既有所有权保护和 B9/B7 的请求/消费提交边界。
4. **避免额外 DB 心跳破坏事务**。当前第二阶段长会话提前读取 AgentRun；若新心跳在另一连接修改该行，Turso 可能产生旧快照冲突。若选持久租约方案，应先重新设计运行记录读取/最终提交边界，再以真实 MVCC 和慢处理测试验证；不能通过长时间持写锁或重放外部副作用规避。
5. **历史数据需要明确升级策略**。旧 running 行没有尝试身份，不能因其年代久远直接判死。优先采用停旧 worker 后审核的迁移或具有足够证明的恢复流程，保护仍存活的旧进程。错误信息须说明中断及统计可能不完整，不虚构已派发数量；历史快照不能偷偷被后续运行重用。
6. 保持 API 既有终态集合，优先用 failed 加明确信息表达中断，除非产品契约确有必要新增状态。任何模型/业务/任务 API/前端表示变更都需同步权威文档。全表无界扫描不是合格回收方案，应明确批次、并发、索引与幂等边界。

上述为实现前约束，不是已经验证的协议。下一轮先定执行归属/状态转换与事务协议，再形成独立原型；不向 main 合入只解决普通异常的半成品。

## 复现证据审查

按 code-review-and-quality 五轴审查本轮文档和探针：正确性方面，四个场景的 20 次子进程退出与两次独立读回均逐项核对，执行源码 SHA 与存档一致；总探针退出 1 是所需不变量失败，不是通过。初次审计脚本误把每场景五次子进程算成六次，断言失败；按探针实际 setup/fail/inspect/recover/inspect 顺序纠正后核对通过，未改动原测试或结果。

可读性与架构方面，探针明确区分处理边界故障注入和未替换的后续 handler，不把队列恢复等同于历史恢复。安全方面，专用 PG 与临时 Turso 仅写合成身份，录制 URL 不发起访问，日志没有外部服务凭证。性能方面，本轮仅四个有界场景，子进程各有 60 秒超时；未引入线上扫描或心跳。Ruff 无缓存检查与 git diff --check 通过。本轮仅批准必要性证据和待实施方案入库，尚无可验收的运行实现。

## 严格验收矩阵

- 双库真实 handler：普通异常、首次记录提交后强制终止、部分成功提交后终止、所有权丢失、主动取消；恢复后不存在已证明终止但仍 running 的行。
- 真正 MemoryQueue 和 RedisQueue/worker 的独立进程：恢复新尝试、不同 Agent 并行、慢任务健康续租、旧进程暂停后恢复、Redis/DB 临时不可用与网络分区；需证明未知所有权不会被当作安全继续或死亡证据。
- 条件更新竞争：回收先于正常完成/正常完成先于回收、重复回收、取消与完成交错；旧结果不覆盖新 run 或 Agent 摘要。真实数据库锁/事务行为，不能仅用 mock 状态代替。
- 旧库升级、缺字段/索引、迁移重复执行、回滚；审核历史记录的保留/终结策略。至少复用固定哈希录制资源，并明确区分真实数据和合成生命周期。
- API 运行历史与有效运行筛选端到端显示终态，保留 B9 请求退避/确认和 B7 消费进度完整回归；不得把历史计数默认为可信。
- 最后正式重基、冻结全部输入，完整单元/API ≥95%、隔离集成 ≥85%、零失败。审计跳过、实际退出、覆盖率导出、测试栈清理及五轴审查后才能关闭 TODO。
